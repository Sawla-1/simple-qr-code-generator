# How It Works

This explains the app code and the deploy workflow, step by step and line by line.

## 1. The app (`src/App.jsx`)

```jsx
const [text, setText] = useState('')
const [submittedText, setSubmittedText] = useState('')
```
Two separate pieces of state:
- `text` — updates on every keystroke (what's currently in the input box)
- `submittedText` — only updates when you click **Generate**

Why two, not one? If we only had `text` and rendered the QR code from it directly,
the QR code would redraw on every single keystroke — including while you're still
mid-word. Splitting it in two means the QR code only updates when you deliberately
click the button.

```jsx
function handleGenerate() {
  setSubmittedText(text)
}
```
Copies whatever is currently typed into `submittedText`. This is the only place
`submittedText` ever changes.

```jsx
<input
  type="text"
  value={text}
  onChange={(e) => setText(e.target.value)}
  ...
/>
```
A "controlled input" — the box's value is always driven by React state (`text`),
and every keystroke calls `setText` to update it. This is the standard React
pattern for form inputs.

```jsx
<button onClick={handleGenerate}>Generate</button>
```
Clicking this is the only trigger that updates `submittedText`.

```jsx
{submittedText && (
  <QRCodeSVG value={submittedText} size={200} />
)}
```
- `submittedText && (...)` — only renders the QR code if `submittedText` is not
  an empty string. Prevents showing a blank/broken QR code before you've typed
  anything.
- `<QRCodeSVG value={submittedText} />` — the whole QR code is generated by this
  one component, from the `qrcode.react` library. It reads `value` and draws the
  QR code as an SVG. No manual canvas drawing needed.

## 2. `vite.config.js`

```js
export default defineConfig({
  plugins: [react()],
  base: '/simple-qr-code-generator/',
})
```
- `plugins: [react()]` — lets Vite understand JSX syntax and enables React fast-refresh during development.
- `base: '/simple-qr-code-generator/'` — GitHub Pages serves this project at
  `https://sawla-1.github.io/simple-qr-code-generator/`, which is a **subfolder**,
  not the domain root. Without `base` set correctly, the built `index.html` would
  request assets like `/assets/index.js` (root-relative), which is the wrong
  path once deployed — the page would load blank with 404s in the console. This
  value must exactly match the repo name.

## 3. The deploy workflow (`.github/workflows/deploy.yml`), line by line

```yaml
name: Deploy to GitHub Pages
```
Just a label — shows up in the "Actions" tab on GitHub so you can identify this workflow.

```yaml
on:
  push:
    branches: [main]
```
**When this workflow runs.** Only triggers on a push to the `main` branch.
Pushes to other branches, or opening a pull request, do NOT trigger it —
that's intentional, so your live site doesn't change until code actually
lands on `main`.

```yaml
permissions:
  contents: read
```
GitHub Actions jobs get **no permissions by default** — you must grant exactly
what's needed. This top-level block is the **default for every job** in the
file: `contents: read` — needed to check out (download) your repo's code.

Following the principle of least privilege, this is kept to the minimum both
jobs need. The `deploy` job needs more (publishing to Pages), but instead of
adding those extra permissions here (which would hand them to `build` too,
even though it never uses them), they're granted only inside the `deploy` job
itself — see below.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
```
Defines a job named `build`, run on a fresh Ubuntu virtual machine that GitHub
provides for free.

```yaml
    steps:
      - uses: actions/checkout@v6
```
Downloads your repo's code onto that virtual machine. Without this, the VM is
empty — there's no code to build.

```yaml
      - uses: actions/setup-node@v7
        with:
          node-version: 20
```
Installs Node.js (version 20) on the VM, so `npm` commands work. The VM doesn't
have Node pre-installed for your specific version by default.

```yaml
      - run: npm install
```
Installs your project's dependencies (React, Vite, qrcode.react) — same as
running it on your own computer.

```yaml
      - run: npm run build
```
Runs the Vite production build — this is the **CI** part. It compiles your code
into a `dist` folder of plain HTML/CSS/JS. If there's a code error, this step
fails and the workflow stops here (nothing broken gets deployed).

```yaml
      - uses: actions/upload-pages-artifact@v4
        with:
          path: dist
```
Packages the `dist` folder and stores it as a build "artifact" that the next
job can use. GitHub Pages deployments specifically require the artifact to be
uploaded this way (not just left in the VM's file system, which gets destroyed
after the job ends).

```yaml
  deploy:
    needs: build
    runs-on: ubuntu-latest
```
A second job, named `deploy`. `needs: build` means it will only start after the
`build` job finishes successfully — this is the **CD** part, kept separate from
CI on purpose (deploy only happens if the build didn't fail).

```yaml
    permissions:
      pages: write
      id-token: write
```
A job-level `permissions` block **replaces** the top-level one for that job —
it doesn't add to it. So `deploy` must list everything it needs itself:
- `pages: write` — needed to publish files to GitHub Pages.
- `id-token: write` — needed for GitHub to issue a short-lived OIDC token that
  proves "this specific workflow run is authorized to deploy." The official
  `deploy-pages` action requires this — without it, the deploy step fails with
  a permissions error.

(Note: `deploy` doesn't need `contents: read` — it never touches your code
directly, it only publishes the artifact that `build` already created.)

```yaml
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
```
Tells GitHub "this job deploys to the `github-pages` environment," which is
what makes GitHub show your live URL directly on the deployment summary page.

```yaml
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```
The actual publish step. Takes the artifact uploaded earlier and publishes it
to GitHub Pages. `id: deployment` lets the `environment.url` line above read
back the resulting live URL.

## Summary

- **CI** = the `build` job (install, build, catch errors early)
- **CD** = the `deploy` job (publish the build output live)
- Every push to `main` re-runs both automatically — no manual redeploying, ever.
